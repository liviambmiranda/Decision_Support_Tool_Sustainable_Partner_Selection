# Sustainable Partner Selection Decision Support

A local MCP server implementing a decision-support method for sustainable partner
selection in the SASB Semiconductors sector: SASB criteria formulation, criterion
weighting by a Group Hierarchical Fuzzy Best-Worst Method (GH-FBWM) over a
`SASB topic -> SASB indicator` hierarchy, LLM scoring of qualitative ESG
disclosures against a fixed rubric, and FlowSort classification of candidate
partners into ordered categories.

This repository contains the material needed to reproduce the study's two
sensitivity analyses.

**Prompt sensitivity.** Four scoring prompts of decreasing detail are compared.
Each of four local LLMs scores every qualitative company-indicator unit under
every prompt; the four model ratings are reduced to their median and that median
is the FlowSort input. Everything else is held at its study value, so any change
in the classification is attributable to the prompt.

**Criterion-weight sensitivity.** Every criterion weight is drawn from a uniform
density over `w * (1 - pct)` to `w * (1 + pct)`, the whole weight vector is
resampled, and FlowSort is re-run on every draw. The company evaluations, the
limiting profiles and the preference function stay fixed, so every reported
difference is attributable to the weights.

**Not in this repository:** the input datasets (see [Input data](#input-data)),
every analysis output and derived table (all of them are regenerated by the
commands in [Reproduction](#reproduction)), the browser client, the human-rater
agreement study, and the limiting-profile and preference-function sensitivity
analyses.

## Requirements

- Python 3.12 (tested on 3.12.13)
- [Ollama](https://ollama.com), for the qualitative scoring calls
- Python packages in `requirements.txt`; `requirements-dev.txt` adds the test
  dependencies

## Input data

No data is distributed here. Create a `data/` directory at the repository root
holding the five files below. Each is a JSON array of flat objects; the field
names are read verbatim by `src/decision_support_mcp/quantitative_scores.py`.

| file | supplies | fields |
| --- | --- | --- |
| `sasb_semiconductors_metadata.json` | the criteria: one record per SASB indicator | `code`, `measure`, `topic`, `domain`, `quantity`, `category`, `explanation` (the SASB guidance text given to the model), `search_terms` |
| `measures_HITL.json` | the **candidate partners** to be classified: one record per company-indicator pair | `code`, `company`, `measure`, `value`, `unit`, `page`, `confidence` |
| `corrected_all.json` | the **reference pool** the limiting profiles are computed from, same shape and a superset of the candidates | `code`, `company`, `measure`, `value`, `unit`, `page`, `confidence` |
| `financial_HITL_equipment.json` | revenue, used as the normalization denominator | `company`, `fiscal_year`, `fiscal_period_end`, `standardized_metric` (`total_revenue`), `reported_metric`, `currency`, `value_millions`, `value` |
| `convertion.json` | currency conversion to USD | `currency`, `usd_per_1_local_currency`, `average_rate_2024_local_per_usd` |

Notes that decide how a record is treated:

- `category` sets the direction and the scoring path. A suffix `LTB` is
  larger-the-better, `STB` smaller-the-better; `Qualitative` indicators are
  larger-the-better and are the ones scored by the prompts. The study set is 18
  indicators, 3 of them qualitative.
- In `measures_HITL.json`, a `value` that is a non-empty string on a qualitative
  indicator is a disclosure to be rated. Missing disclosures are excluded from
  the rater set and receive the worst limiting profile in FlowSort instead.
- Company names must be spelled identically across the three company files; the
  loader fails loudly on an unmatched name rather than dropping it.
- Everything the pipeline writes also lands under `data/`, and `.gitignore`
  keeps the whole directory out of version control.

## Study configuration

Fixed values, all defined in code rather than passed on the command line.

| parameter | value | defined in |
| --- | --- | --- |
| models | `llama3.1:8b`, `qwen3.5:9b`, `deepseek-v2:16b`, `gemma4:12b` | `rating_evaluation/prompt_sensitivity.py` (`DEFAULT_MODELS`) |
| temperature / top-p | `0.0` / `1.0` | `prompt_sensitivity.py`, `collect.py` |
| iterations per (model, prompt, unit) | 100, seed = iteration index | `DEFAULT_ITERATIONS` |
| rating scale | integers 1-5 | `rating_evaluation/prompts.py` (`RATING_LABELS`) |
| system prompt | none sent | `prompts.py` (`SYSTEM_PROMPT`) |
| aggregation over models | median, ties resolved downward | `rating_evaluation/agreement.py` (`median_lower`) |
| criterion weights | the study's GH-FBWM vector, 14 criteria | `flowsort.py` (`GH_FBWM_STUDY_WEIGHTS`) |
| FlowSort mode / rule | limiting profiles / net flow | `flowsort.py` |
| preference function | `t1` usual criterion, `q = 0`, `p = 0` | `flowsort.py` |
| categories | `C1`, `C2`, `C3` | `flowsort.py` (`CATEGORY_LABELS`) |
| Monte Carlo draws | 10,000, uniform density | `sensitivity_analysis.py` (`MONTE_CARLO_DEFAULT_SAMPLES`) |
| Monte Carlo range | `--pct 0.20` is the CLI default; the module default is `0.10` | `run_weight_monte_carlo.py`, `sensitivity_analysis.py` |
| Monte Carlo seed | 42 | `run_weight_monte_carlo.py` |

## Prompts

The four prompts differ only in how much scaffolding they give the model, which
is what isolates the effect of prompt detail on the classification. They are
frozen: every stored rating carries the SHA-256 of the prompt that produced it,
so an edited prompt is detected instead of silently mixed into an existing
collection.

| prompt | SASB guidance | scoring rubric | SHA-256 of the template |
| --- | --- | --- | --- |
| `prompt_1` | yes | yes | `049a16b8ad33f44b5579edbda864ef11712b32226f1c6168ca92168071d70e53` |
| `prompt_2` | no | yes | `64b4635501980466296f96ee3814db508d8b24a9424d29e15bea5276cda62c09` |
| `prompt_3` | yes | no | `6ed4bd28aaf4686cee1c273178c419d08a61824beac89e1bf3c4a2c7abce8d80` |
| `prompt_4` | no | no | `b8214a575d26ff9096bb45e9aecce7b465fc39b5ffcce74b27ec533d9291d89d` |

Rubric SHA-256:
`22ba8afb41129783a0fb7f3501ba11d82ed4adc5d0f7ba07ac6bdb536e402fb2`.

`prompt_1` is the study baseline and is not redefined for the analysis: it is
`SCORING_PROMPT` from `rating_evaluation/prompts.py` imported, the same text the
live tool scores with. The four templates and the rubric are in
`rating_evaluation/prompt_sensitivity_prompts.py` and `prompts.py`; once `data/`
is in place they can also be printed filled in with a real unit:

```bash
.venv312/bin/python scripts/run_prompt_sensitivity.py show-prompt --rendered
```

## Reproduction

Run the steps in order from the repository root, with Ollama running.

**1. Check the scope and the call budget.** Prints the units resolved from your
data, the prompts and the number of calls the collection will make.

```bash
.venv312/bin/python scripts/run_prompt_sensitivity.py scope
```

**2. Collect the ratings.** Appends to
`data/prompt_sensitivity/llm_ratings_by_prompt.jsonl` and resumes from whatever
is already on disk, so an interrupted run is restarted with the same command.
Models are loaded once each and held with `keep_alive`, because a model swap
costs minutes against seconds for a warm call.

```bash
.venv312/bin/python scripts/run_prompt_sensitivity.py collect
```

**3. Aggregate, classify and compare the prompts.** Refuses to compare prompts
whose collections are incomplete, since they would rest on different samples.

```bash
.venv312/bin/python scripts/run_prompt_sensitivity.py report
```

**4. Classify per model as well as per prompt.** Writes the per-series
qualitative score files that step 5 reads.

```bash
.venv312/bin/python scripts/run_flowsort_by_model.py
```

**5. Run the weight Monte Carlo.** `run` is one simulation on one scoring
series; `--series median` is the study baseline, a model tag swaps in that single
model's ratings under an identical weight protocol.

```bash
.venv312/bin/python scripts/run_weight_monte_carlo.py run --series median --samples 10000 --pct 0.20
```

`by-series` repeats the identical protocol on every model and on their median.
Several `--pcts` or `--seeds` repeat the whole comparison at each value: the
range sweep locates where each series breaks, the seed sweep separates a property
of the ratings from a property of the sample path.

```bash
.venv312/bin/python scripts/run_weight_monte_carlo.py by-series --samples 10000 --pcts 0.05 0.10 0.15 0.20 --seeds 42 1 7 123
```

**6. Optional: read the prompt effect against the category margins.** Records,
per (prompt, series, candidate), the net flow and the margin to each bounding
profile, which separates a category that changed because the prompt moved the
score from one that changed because it was on a knife edge.

```bash
.venv312/bin/python scripts/run_prompt_boundary_analysis.py
```

The `--series human:<rater>` and `--include-humans` options of step 5 read expert
score files from `data/eval/scores_by_human/`. Those belong to the human-rater
study, which is not part of this repository; without them, use the model series
and the median.

### Where the outputs go

| path | written by |
| --- | --- |
| `data/prompt_sensitivity/llm_ratings_by_prompt.jsonl` | step 2, one record per call |
| `data/prompt_sensitivity/csv/` | steps 3, 4, 6 — ratings, medians, classifications, pairwise agreement, rankings, boundary margins |
| `data/prompt_sensitivity/json/consensus/` | step 3, the medians fed to FlowSort |
| `data/prompt_sensitivity/json/scores_by_model/` | step 4, the per-series qualitative scores |
| `data/prompt_sensitivity/json/prompt_sensitivity_result.json` | step 3, the full result |
| `data/monte_carlo/` | step 5, one CSV set per run: draws summary, per company, per criterion, convergence |

## Running the tool itself

The MCP server exposes the criteria resources and the GH-FBWM, FlowSort and
sensitivity tools:

```bash
.venv312/bin/python server.py
```

`client.py` is a command-line MCP client for the same server.

## Tests

Both suites read the datasets, so `data/` has to be populated first. No LLM call
and no Ollama instance is needed: the ratings are stubbed.

`tests/test_prompt_sensitivity.py` covers the prompt analysis — median
aggregation, the provenance guard on an edited prompt, resuming a collection,
the refusal to compare incomplete coverage, and the comparison tables:

```bash
.venv312/bin/python -m pytest tests -q
```

`tests/smoke_test.py` is a standalone script rather than a pytest module. It
exercises the server end to end: the SASB resources, GH-FBWM, FlowSort and the
weight Monte Carlo.

```bash
.venv312/bin/python tests/smoke_test.py
```
